# KernelLake AWS Benchmark Harness

**Unofficial, TPC-H-*derived* benchmark. Not a certified TPC-H result.**
Reuses `tools/generate_tpch.py` (a synthetic TPC-H-shaped generator, not the
official `dbgen`) and `benchmarks/tpch/queries/` (6 of TPC-H's 22 queries —
the only ones KernelLake's SQL engine supports today; see "Query coverage"
below). See `../../NOTICE` and `../../docs/TPCH.md` for the same caveats
this harness inherits.

## What this measures, and why

The headline question this harness exists to answer: **if KernelLake
finishes common analytical queries meaningfully faster than a CPU-based
engine (PySpark) while running on cheap infrastructure, how much faster,
and at what cost per query?** Three numbers matter most:

1. **Latency speedup ratio** — `median(PySpark latency) / median(KernelLake latency)`,
   per query, per scale factor.
2. **Cost per completed query** — actual AWS spend for a run, divided by
   queries finished.
3. **Concurrency behavior** — does that per-query latency/cost advantage
   hold, shrink, or grow as concurrent query load increases?

Scan throughput (physical S3 MB/s, logical TB/s) and cost per TB scanned
are also computed, but as **supporting/mechanism metrics** that explain
*why* the headline numbers look the way they do — not the top-line result
themselves.

## What this does *not* measure (and why)

- **True distributed multi-node scaling.** KernelLake has no distributed
  query execution today (`docs/ROADMAP.md` lists it as an explicit
  non-goal) — `kernellake-server` replicas are fully independent, no
  coordinator, no shuffle. "Scaling" here means **concurrent-query
  throughput** across independent replicas (real and testable), not a
  single query getting faster by adding nodes. PySpark's own worker-count
  scaling (a real concept for Spark) is measured as originally specified.
- **16 of TPC-H's 22 queries.** Only Q1, Q3, Q6, Q12, Q14, Q19 run on
  KernelLake today — the rest need SQL features (correlated subqueries,
  `EXISTS`, `DECIMAL`, `HAVING`, non-equi joins) the engine doesn't support
  yet. Every report generated by this harness lists the other 16 as
  explicitly blocked, with why — never silently omitted.
- **DataFusion / Polars / Athena / Databricks Photon / Snowflake.** The
  runner's engine model is a pluggable adapter (see
  `runner/aws_benchmark_runner.py`, mirroring `tools/benchmark_three_way.py`),
  so adding one later doesn't require rearchitecting — but none of these
  are wired up this phase.
- **DuckDB has two modes.** `runner/duckdb_query_loop.py` runs it on its
  own dedicated, single-node, cost-tracked EC2 host
  (`terraform/duckdb_instance.tf`, node-count-matched against the
  KernelLake/Spark hosts) — a real latency *and* cost comparison, included
  in every table like KernelLake/PySpark. `aws_benchmark_runner.py`'s
  older `--duckdb` flag still runs it in-process on whichever host runs
  the orchestrator instead, for a quick sanity check with no infra to
  provision — excluded from cost tables in that mode only, since there's
  no dedicated $/hour to attribute a query's cost against. See
  docs/RUNBOOK.md for both.

## Real AWS costs — read this before running anything

Every command under `terraform/` and `scripts/` that can create real AWS
resources is called out below. **Nothing in this directory provisions
infrastructure or spends money by import/inclusion alone** — `terraform
apply`, the data-generation scripts, and the benchmark runner all require
an explicit, separate invocation, and the largest ones
(`scripts/estimate_cost.py`) print a dollar estimate you must confirm
before they proceed. See `docs/COST_ESTIMATES.md` for real observed costs
per milestone, and `docs/RUNBOOK.md` for the exact command sequence.

Rough shape of the cost curve (see `docs/COST_ESTIMATES.md` for live
numbers once M1 has actually run): a single validated small run at SF100 is
inexpensive (low tens of dollars); SF10000 (~10TB) is the most expensive
and slowest step in the whole project by data volume; the 8-replica
concurrency test is the most expensive *single* step by simultaneous
instance-hours (8x `g6.8xlarge` running at once, time-boxed and torn down
immediately after).

## Prerequisites

- AWS credentials with permission to create EC2 instances, S3 buckets, IAM
  roles/instance profiles, and security groups in the target region
  (`us-east-1` by default).
- Terraform >= 1.5.
- Python 3.11+ with `boto3` for the local orchestration scripts.
- An existing EC2 key pair name, and your own IP/CIDR for SSH access.
- **No manual Docker build/push needed**: `kernellake_docker_image` defaults
  to `ghcr.io/hurdad/kernel-lake-gpu:latest`, which this repo's own CI
  (`.github/workflows/docker-publish.yml`) already builds and pushes on
  every push to `main`. Only build and push your own image (and override
  `kernellake_docker_image`) if you're testing local changes not yet on
  `main` — see `docs/RUNBOOK.md`.

## Quickstart (M0 → M1)

See `docs/RUNBOOK.md` for the full, milestone-by-milestone sequence. M0
(this codebase) requires no AWS access at all:

```bash
cd benchmarks/aws/terraform
terraform init
terraform validate
terraform plan   # review; creates nothing
```

M1 (first real, small, cost-confirmed run) begins with:

```bash
python3 ../scripts/estimate_cost.py --milestone m1
# review the printed estimate, then:
../scripts/provision.sh --yes
```

## Layout

```
benchmarks/aws/
  terraform/     Infrastructure as code (EC2, S3, IAM, networking, monitoring instance)
  scripts/       Cost estimation, provisioning, data generation/upload, teardown
  runner/        The benchmark orchestrator (KernelLake + PySpark, remote, S3-backed; optionally + DuckDB via --duckdb, in-process)
  monitoring/    Prometheus, OTel Collector, Grafana dashboards
  reporting/     Result aggregation, Markdown/CSV/JSON report, interactive HTML dashboard
  docs/          RUNBOOK.md (step by step), COST_ESTIMATES.md (real observed costs)
```
